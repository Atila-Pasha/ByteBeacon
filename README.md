ByteBeacon is a FastAPI-based monitoring service that checks public HTTP and
HTTPS endpoints on a schedule, records availability and latency, tracks
incidents, and can deliver notifications through Telegram.

> **Project status:** ByteBeacon is under active development. APIs and
> configuration may change between releases.

## Highlights

- User registration and cookie-based access and refresh-token authentication
- Monitor creation, listing, updating, activation, and deletion
- Configurable check intervals and request timeouts
- Check history with status codes, latency, and error details
- Automatic incident creation and recovery tracking
- Telegram account linking and incident notifications
- OpenAPI documentation generated by FastAPI
- Async PostgreSQL access through SQLAlchemy and `asyncpg`
- Alembic migrations for database schema management

## Architecture

```text
										+------------------+
										|  FastAPI service  |
										+---------+--------+
															|
						 +----------------+----------------+
						 |                                 |
			REST API / auth                  Monitor scheduler
						 |                                 |
						 +----------------+----------------+
															|
										+---------v--------+
										|    PostgreSQL    |
										+------------------+
															|
										Public HTTP/HTTPS
											 monitor targets
```

The scheduler reconciles active monitors and runs checks at each monitor's
configured interval. A check is considered successful for HTTP status codes
from `200` through `399`. Monitor targets must resolve exclusively to public
IP addresses; private and loopback destinations are rejected.

## Requirements

- Python 3.10 or newer
- PostgreSQL 13 or newer
- A virtual environment is recommended
- Telegram credentials are required only for Telegram integration

## Quick start

### 1. Clone and enter the repository

```bash
git clone <repository-url>
cd ByteBeacon
```

### 2. Create a virtual environment

```bash
python -m venv .venv
source .venv/bin/activate
```

On Windows, activate the environment with:

```powershell
.venv\Scripts\Activate.ps1
```

### 3. Install dependencies

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Configure the environment

Create a local environment file from the example:

```bash
cp .env.example .env
```

Set valid PostgreSQL connection strings and replace `SECRET_KEY` with a long,
random value. Configure the Telegram variables only when Telegram support is
needed. Never commit `.env` or any other file containing credentials.

### 5. Create the database schema

```bash
alembic upgrade head
```

### 6. Start the API

```bash
uvicorn app.main:app --reload
```

The service is available at `http://127.0.0.1:8000`.

Interactive API documentation is available at:

- Swagger UI: `http://127.0.0.1:8000/docs`
- ReDoc: `http://127.0.0.1:8000/redoc`
- Health check: `http://127.0.0.1:8000/health`

## API overview

All application routes are prefixed with `/v1`. Protected routes authenticate
using the HTTP-only cookies created by the login and refresh endpoints, or an
`Authorization: Bearer <token>` header.

| Area | Method | Endpoint | Authentication |
| --- | --- | --- | --- |
| Health | `GET` | `/health` | Public |
| Auth | `POST` | `/v1/auth/register` | Public |
| Auth | `POST` | `/v1/auth/login` | Public |
| Auth | `POST` | `/v1/auth/refresh` | Refresh cookie |
| Auth | `POST` | `/v1/auth/logout` | Optional refresh cookie |
| Users | `GET` | `/v1/users/me` | Required |
| Monitors | `GET`, `POST` | `/v1/monitors` | Required |
| Monitor | `GET`, `PATCH`, `DELETE` | `/v1/monitors/{monitor_id}` | Required |
| Checks | `GET` | `/v1/monitors/{monitor_id}/checks` | Required |
| Incidents | `GET` | `/v1/monitors/{monitor_id}/incidents` | Required |
| Telegram | `POST` | `/v1/users/me/telegram/token` | Required |
| Telegram | `GET`, `DELETE` | `/v1/users/me/telegram` | Required |
| Telegram | `POST` | `/v1/telegram/connect` | Public token exchange |

Monitor intervals are expressed in minutes and must be greater than zero.
Monitor URLs must use `http://` or `https://` and resolve only to public IP
addresses.

## Configuration

Copy `.env.example` to `.env` and provide values for the required settings.

| Variable | Required | Default | Purpose |
| --- | --- | --- | --- |
| `APP_NAME` | No | `ByteBeacon` | Application name |
| `APP_VERSION` | No | `0.1.0` | API version displayed by FastAPI |
| `DEBUG` | No | `false` | Enables development behavior, including non-secure cookies |
| `DATABASE_URL` | Yes | None | Async SQLAlchemy PostgreSQL URL |
| `DATABASE_SYNC_URL` | Yes | None | Synchronous PostgreSQL URL for Alembic |
| `SECRET_KEY` | Yes | None | JWT signing key |
| `ALGORITHM` | No | `HS256` | JWT signing algorithm |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | No | `15` | Access-token lifetime |
| `REFRESH_TOKEN_EXPIRE_DAYS` | No | `7` | Refresh-token lifetime |
| `CHECK_TIMEOUT` | No | `10.0` | HTTP check timeout in seconds |
| `SCHEDULER_ENABLED` | No | `true` | Starts the monitor scheduler in this process |
| `TELEGRAM_BOT_TOKEN` | No | Empty | Telegram bot token |
| `TELEGRAM_BOT_USERNAME` | No | Empty | Telegram bot username for linking |
| `TELEGRAM_LINK_EXPIRE_MINUTES` | No | `10` | Telegram linking-token lifetime |
| `TELEGRAM_API_TIMEOUT` | No | `10.0` | Telegram API timeout in seconds |
| `TELEGRAM_API_BASE_URL` | No | `http://localhost:8000` | API base URL used by Telegram integration |
| `TELEGRAM_PROXY_URL` | No | Empty | Optional SOCKS proxy for Telegram traffic |

## Telegram integration

To link an account, an authenticated client requests a short-lived Telegram
connection token from `POST /v1/users/me/telegram/token`. The response includes
a Telegram start link. After the bot receives the link, the connection is
completed through `POST /v1/telegram/connect`.

Provide `TELEGRAM_BOT_TOKEN` and `TELEGRAM_BOT_USERNAME` in `.env` to enable
the integration. `TELEGRAM_PROXY_URL` can be set when the Telegram API is only
reachable through a proxy.

## Development

Run the test suite with:

```bash
pytest
```

Run a focused test module with:

```bash
pytest tests/monitoring/test_checker.py -q
```

Create a new migration after changing models:

```bash
alembic revision --autogenerate -m "describe the schema change"
alembic upgrade head
```

## Deployment

Run the scheduler in exactly one process or deployment replica. Set
`SCHEDULER_ENABLED=false` on API-only replicas, and enable it only for the
dedicated monitoring worker. Otherwise every replica checks every monitor and
creates duplicate check records and notifications.

Run database migrations as a release step before starting application
processes. Keep `DEBUG=false` in production, use a unique high-entropy
`SECRET_KEY`, and store all secrets in the deployment platform's secret
manager.

Because the scheduler performs outbound requests, deploy it with network
egress access while retaining the application's public-target validation.
